# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**J.A.W.S** ("Just Automated Web Scanner" — BrowserGym PPO Web Error Detection) drives a PPO reinforcement-learning
agent through real websites via **BrowserGym + Playwright**, diffing the observation before and after each action to
detect GUI/runtime bugs without relying on hand-written test scripts. Detected anomalies are optionally matched
against a per-site `bug_catalog.json` for precision/recall evaluation, or left as open-ended findings for human
review when no catalog exists.

Detected bug types: `button-no-response`, `form-no-feedback`, `layout-overlap`, `layout-overflow`,
`duplicated-rendering`, `network-error`, `api-ui-mismatch`, `api-forbidden`.

## Environment setup

- Python 3.12. `BrowserGym/` is a vendored copy of the BrowserGym package with its own `pyproject.toml`
  (`pip install -e BrowserGym`). It is gitignored (not pushed to GitHub) — treat it as a local dependency checkout,
  not project source to edit casually.
- Two venvs may exist locally: `BrowserGym\.venv` (per README, used for manual/team setup) and a root `.venv`
  (used by `.github/workflows/jaws-port-batch-training.yml`). **There is currently no committed root
  `requirements.txt`**, even though the README's manual setup instructions and the CI workflow both reference one —
  CI silently no-ops if it's missing and relies on `pip install -e BrowserGym` alone. If dependencies are missing
  (torch, numpy, jinja2, etc.), check which venv actually has packages installed before assuming setup is broken.
- Shared PPO checkpoint: `artifacts/models/jaws_browsergym_shared_ppo.pt`, tracked via **Git LFS**
  (`git lfs pull` after clone). `artifacts/`, `configs/generated/`, and per-site checkpoints are otherwise
  gitignored — they're regenerated by running the pipeline, not part of the repo.

## Common commands

All commands below assume the venv's python, e.g. `.\BrowserGym\.venv\Scripts\python.exe`.

**Single-site training / evaluation:**
```powershell
python runners\train_multisite_browsergym_agent.py --config configs\training_sites.json --total-updates 20 --episodes-per-site 1 --max-steps 25
python runners\evaluate_multisite_browsergym_agent.py --config configs\training_sites.json --model-path artifacts\models\jaws_browsergym_shared_ppo.pt --episodes 3 --max-steps 25
```

**Port-range batch automation** (the main entry point for exploring many locally-running sites at once):
```powershell
python scripts\run_all_port_batches.py --start-port 9220 --end-port 9229 --batch-size 10 --total-updates 5 --episodes-per-site 1 --max-steps 15 --eval-episodes 1
```
This orchestrates, in order: `generate_port_sites_config.py` → `preflight_port_sites.py` (splits sites into
`active_sites.json` / `failed_sites.json` by doing a real env reset per site) → `create_site_batches.py` →
`run_batch_training.py` (per batch) → `run_batch_evaluation.py` (per batch) → `merge_batch_results.py` → final
summary printed to stdout. A single batch's train/eval failure is recorded in `failed_batches.json` but does not
abort the run. Also runnable as a GitHub Actions `workflow_dispatch` job
(`.github/workflows/jaws-port-batch-training.yml`, self-hosted runner).

Success is judged by `training success=true` / `evaluation success=true` / `failed_sites=0` in the summary —
`average_recall`/`average_precision` being `null` is expected for sites with no `bug_catalog.json` (open-ended
discovery mode, no ground truth to score against).

**HTTP API bridge** (used by an external Spring backend to trigger on-demand scans):
```powershell
python runners\browsergym_api_server.py --host 0.0.0.0 --port <port> --model-path artifacts\models\jaws_browsergym_shared_ppo.pt
```
Exposes `POST /explorations/start` / `POST /explorations/{id}/stop`, backed by `services/scan_backend_service.py`,
which spawns `evaluate_multisite_browsergym_agent.py` as a subprocess per scan.

**Tests:**
```powershell
python -m unittest discover -s tests
# or run a single file/test:
python -m unittest tests.test_action_opportunity_engine
python -m unittest tests.test_action_opportunity_engine.SomeTestClass.test_something
```
All `tests/*.py` use `unittest.TestCase` (no pytest fixtures, no `conftest.py`). They are pure unit tests: they
build hand-crafted observation dicts and call service functions directly — no real browser or live server is
started. Several test files import private helpers directly out of runner scripts (e.g.
`runners.evaluate_multisite_browsergym_agent._action_budget_status`), so those runners double as testable modules,
not just CLI entry points — keep that in mind before refactoring their internals.

Note: `scripts/test_browsergym_jaws_env.py` and `scripts/test_browsergym_openended.py` are **not** part of the
`tests/` suite — they're standalone argparse-driven manual scripts that exercise a real `BrowserGymJAWSEnv` against
a live local site (e.g. `--base-url http://localhost:9220`), used for manual smoke-checking a site before batch
training.

## Architecture

Data flows in one direction through five layers; each layer is a plain-dict/dataclass boundary, which is why the
services are unit-testable without a browser:

```
BrowserGymJAWSEnv (envs/browsergym_jaws_env.py)
  → BrowserGymObservationAdapter.convert()  (adapters/browsergym_observation_adapter.py)
  → ObservationEncoder → PPOActorCritic / PPOAgent  (models/, agents/)
  → BrowserGymActionAdapter.adapt() → executable BrowserGym action string  (adapters/)
  → env.step() executes it via Playwright, rebuilds the next observation
  → services/anomaly_detection_service.py diffs prev/next observation → anomaly candidates
  → services/autonomous_reward_service.py turns anomalies/opportunities into a PPO reward
  → services/known_bug_matcher.py (evaluation-only) matches anomalies to bug_catalog.json
```

**`envs/browsergym_jaws_env.py`** wraps `gym.make("browsergym/openended", ...)`. `step()` always returns reward
`0.0` — reward is computed entirely outside the env, in `autonomous_reward_service.py`, from the diffed
observations. This split matters: don't add reward logic to the env. The env also installs Playwright listeners
for console/pageerror/request/response/requestfailed and dispatches ~80 `action_type`s, including several families
(`inspect_*`, DB "hook", trace-correlation, API-contract, login-scenario) that are largely heuristic/synthetic
info-producers driven by `site_profile` opt-in, not real external integrations — don't assume they talk to a real
DB or tracing backend unless you verify it for a specific site.

**`adapters/browsergym_observation_adapter.py`** (~2100 lines) is the core feature-engineering layer. It merges
candidate elements from four sources (AXTree, `extra_element_properties`, manual DOM walk, an injected Playwright
JS extractor) plus a heuristic "infra dashboard" candidate path, computes ~60 derived fields per candidate
(`_make_candidate`), then **strips bug-catalog metadata before the observation reaches the policy**
(`_strip_policy_candidate_metadata`). This "policy-safe" boundary — the RL policy must never see catalog/bug-id
labels, only observed browser state — is enforced deliberately and has dedicated tests
(`tests/test_policy_label_leakage.py`, `tests/test_policy_safety_no_metadata_leakage.py`,
`models/observation_encoder.py::validate_policy_input_schema`). Preserve this separation in any change that touches
observation building, reward, or the encoder.

**`models/action_space.py`**: discrete action id = `action_type_id * max_candidates + candidate_index`.
`build_action_mask()` is the real behavior-shaping layer — it masks invalid candidates, gates whole action families
(infra/login/API-probe/DB/trace/contract) behind availability flags, and layers priority overrides (e.g. force
`fill_input` on the password field once email is filled) driven by `history["action_opportunities"]` /
`history["login_flow"]` state built in `services/action_opportunity_service.py` and
`services/browsergym_training_service.py`.

**`models/dom_graph_builder.py`** builds a graph representation intended for a future GNN encoder — it is not
currently wired into `PPOActorCritic`/`ObservationEncoder`; treat it as unused-in-training scaffolding unless you
find a new call site.

**`agents/ppo_agent.py`**: standard clipped-surrogate PPO over `PPOActorCritic` (+ optional GRU `MemoryEncoder`).
`_load_compatible_policy_state` does partial-shape loading (grows/truncates `shared.0.weight`, `actor.weight/bias`)
so one shared checkpoint (`artifacts/models/jaws_browsergym_shared_ppo.pt`) can keep training even after the
action/observation schema grows — don't assume a checkpoint's obs_dim/action_dim exactly matches current code.

**Services split by concern, not by pipeline stage** — most are shared between training and evaluation:
- `anomaly_detection_service.py` — before/after diffing → anomaly candidates (delegates to
  `web_error_finding_service.py`, `extended_policy_oracle_service.py`).
- `known_bug_matcher.py` — evaluation/labeling only; matches anomalies to a site's `bug_catalog.json`. Never feeds
  the policy.
- `autonomous_reward_service.py` — the actual PPO reward, from anomaly/opportunity/repeat-action signals; keeps
  known-bug bonuses and catalog metadata out of the pre-action policy input.
- `action_opportunity_service.py` — "what can still be done" engine that feeds the action mask and gates
  `finish_episode`.
- `browsergym_training_service.py` — single-site training service; also the shared-helper module
  (`_enrich_action`, `_update_history`, `_update_login_flow_state`, `_guided_action_id`) that
  `multisite_training_service.py` and `evaluate_multisite_browsergym_agent.py` both import.
- `multisite_training_service.py` — the production training path: shared PPO across multiple sites/episodes per
  update round, merged rollouts (see `agents/rollout_buffer.py::extend`).
- `scan_backend_service.py` — on-demand single-URL scan launcher for the HTTP API bridge; spawns
  `evaluate_multisite_browsergym_agent.py` as a subprocess.
- `policy_safe_metrics.py` — precision/recall/F1 and signal-discovery metrics for the "v3 policy-safe" evaluation
  format.
- `browsergym_report_data_builder.py` — joins training/eval JSON artifacts into the dict consumed by the PDF report
  pipeline.

**Reporting**: `browsergym_report_data_builder.py` → `reports/generate_pdf_report.py` →
`exporters/pdf_report_exporter.py`, which renders `reports/templates/error_report_template.html` via Jinja2 and
converts it to PDF using a **headless Playwright Chromium page** (`page.pdf(...)`), not a PDF library — the
reporting path also depends on Playwright being installed.

## Config shape

Site lists (`configs/training_sites*.json`, `configs/evaluation_reference_sites.json`) share the shape:
`{shared_model_path, output_dir, sites: [{site_id, base_url, has_bug_catalog, bug_catalog_path, reward_scale,
exploration_profile?, requires_login?, login?}]}`. `configs/api_sites.json` is a separate shape for API-contract
testing (`{sites: [{site_id, base_url, health_check, apis: [{api_id, method, path, ..., expected_status}]}]}`).
Generated/derived configs live under `configs/generated/` (gitignored, produced by the port-batch pipeline).

## Known documentation gaps

- `docs/browsergym_single_ppo.md` states an observation vector shape of `(653,)` and action dim `(224,)` — these are
  stale relative to the current `ActionSpace.action_types` list (~80 types), which yields a much larger action_dim.
  Don't treat those numbers as current; compute from `ObservationEncoder.get_obs_dim()` /
  `len(ActionSpace.action_types) * max_candidates` instead.
- The README's manual setup steps assume a root `requirements.txt` that isn't committed (see Environment setup
  above).
